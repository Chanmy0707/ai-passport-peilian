# 智能陪练功能设计与实现方案（AI Passport 终端 + 陪练服务端）

日期：2026-11-22　范围：把智能陪练功能设计并实现到 AI Passport 终端（固件），并在 peilian/server 内自建陪练对话服务，端到端跑通"选场景 → 对话 → 评分摘要"。

---

## 1. 概述

MVP 设计文档（[MVP设计文档.md](../../MVP设计文档.md) §3.3/§4.2）已定义陪练模式的高层设计，但代码现状是：固件侧陪练零实现（主菜单"陪练"项置灰），服务端只有场景/角色 CRUD 与设备场景拉取，没有陪练对话服务与评分落库。

交付物（已与用户确认）：

1. **《智能陪练详细设计.md》**（工作区根目录）：终端侧 + 陪练服务端的详细设计文档；
2. **固件实现**：xiaozhi-esp32 固件 `main/mvp/` 内实现陪练模式（场景菜单、对话页、评分页、set_scenario、多服务端连接），可编译可验证；
3. **陪练服务端实现**：在现有 `peilian/server`（FastAPI）内自建小智协议陪练 WS 服务 + 对话管线（MiMo ASR/LLM/TTS）+ 评分落库（用户已选定此方案，替代 MVP 文档 §2.3 的 xiaozhi-esp32-server 选型）。

## 3. 变更明细

### 3.1 设计文档（新文件 `/home/zcm/AIpassport/智能陪练详细设计.md`）

对齐 MVP 设计文档深度，章节：

1. **终端侧设计**：陪练模式状态机分支（主菜单→场景选择→对话→评分摘要→返回场景列表/主菜单）；三个页面的 LVGL 布局与按键语义（对齐 MVP 文档 §3.5 的线框）；倒计时与状态轮换（聆听中/思考中/说话中）；降级表现（TTS 失败文本上屏、LLM 超时固定话术、断连退避重连，对齐 §8）。
2. **协议契约**：以小智 WebSocket 协议为基线（hello 握手、二进制音频帧、`listen/tts/stt` 状态、`tts.stop` 打断），定义两处扩展：
   - `set_scenario` MCP 工具调用（设备→服务，携带 `scenario_id`；服务端回 MCP 结果含角色名，失败 `SCENARIO_NOT_FOUND`）——沿用 MVP 文档 §5.2 I2；
   - **新增** `practice` 消息族（服务→设备）：`{"type":"practice","event":"report","data":{overall_score, duration_s, turns, feedback}}` 评分摘要下发；`{"type":"practice","event":"tick","data":{remaining_s}}` 可选倒计时同步。设备侧在 `application.cc` 的 `OnIncomingJson` 将 `practice` 类型转发给 MvpApp 处理。
3. **陪练服务端设计**：WS 会话状态机（hello→idle→listening→thinking→speaking）；对话管线（收 Opus 帧 → 静音判停 → Opus 解码 16k PCM → MiMo ASR → MiMo LLM 结构化输出 `{reply, score, feedback}` → MiMo TTS 流式 PCM16 → Opus 编码回传）；评分落库与会话收尾（时长用尽/主动结束/断连超时 5 分钟）；mock 模型层（供冒烟测试）。
4. **数据模型**：`practice_session` / `practice_turn` 建表语句（字段对齐 MVP 文档 §6.1）。
5. **改动清单**：固件/服务端逐文件改动点（即本方案 §3.2/3.3 的固化）。

同步修订 [MVP设计文档.md](../../MVP设计文档.md) §2.3"陪练服务"选型行：xiaozhi-esp32-server → peilian/server 内自建小智协议子集（注明原因：与既有 FastAPI 录音服务/场景 CRUD/数据库同栈，避免双服务维护，2026-11-22 评审确认）。

### 3.2 固件实现（`peilian/firmware/xiaozhi-esp32/`，全部落在 `main/mvp/` + 两处核心文件小改）

| 文件 | 改动 | 说明 |
|---|---|---|
| `main/mvp/mvp_ui.{h,cc}` | 新增三页面 | ① 场景选择页：列表（名称+选中项下方显示说明与"限 N 分钟"），UP/DOWN 选择、OK 开始；② 对话页：顶部"陪练·{场景}"、倒计时、状态轮换、最近一句滚屏（按 §3.5 线框）；③ 评分摘要页：分数+进度条+用时/轮数+一句反馈，OK 返回场景列表。仍走 DisplayLockGuard + esp_timer 刷新模式 |
| `main/mvp/mvp_app.cc` | 陪练编排 | 菜单项"陪练"解除置灰；`EnterSelected()` 接 `MODE_PRACTICE`：进模式拉取场景列表（HTTP `GET /api/v1/devices/{id}/scenarios`，失败回落 NVS 缓存）→ 场景页 → 对话会话（打开音频通道、按键说话、倒计时）→ 结束时发会话结束请求 → 收到 `practice.report` 显示评分页。倒计时以场景 `duration_minutes` 本地计时为主（服务端兜底强制收尾） |

| `main/mvp/mode_manager.{h,c}` | 接线 | `MODE_PRACTICE` 进出状态流转（如需持久化当前模式才改，否则不动） |
| `main/mcp_server.cc` | 注册工具 | `AddTool()` 注册 `set_scenario`（参数 `scenario_id`，回调把调用转发给 MvpApp 的场景切换处理） |
| `main/application.cc` | 两处小改 | ① `OnIncomingJson` 增加 `practice` 类型消息转发 MvpApp（现有 `notify`/`tts` 分支旁加分支）；② 音频分流处（约 :276-278）确认陪练对话音频走 `protocol_`（与日常对话一致，无需改） |
| 多服务端连接 | 连接编排（落在 `mvp_app.cc`） | 进入陪练对话前：缓存 OTA 下发的 `Settings("websocket")` 原值，写入 `practice_ws_url`/token，再 `OpenAudioChannel()`；退出陪练/进日常对话时恢复原值重连。`websocket_protocol.cc` 不改（其每次开通道读 NVS 的特性正好支持该机制）。遵守 AGENTS.md：状态变更走 `SetDeviceState()`、回调 `Schedule()` 回主线程 |

约束遵守：板型门控沿用 `CONFIG_BOARD_TYPE_FOLOTOY_AI_PASSPORT`；新增中文文案注意 LVGL 字体子集覆盖；采样率统一 16kHz（板级 config 现为 24kHz，实现时优先对齐板级到 16kHz 并回归日常对话，构建验证见 §5）。

### 3.3 陪练服务端实现（`peilian/server/`）

| 文件 | 改动 | 说明 |
|---|---|---|
| `schema.sql` | 新增 2 表 | `practice_session`（id, device_id, scenario_id, started_at, ended_at, overall_score, status）+ `practice_turn`（id, session_id FK, role user/ai, content, score, feedback, ts）；对齐 §6.1；注释同步更新 |
| `app/practice/`（新包） | 对话管线 | `ws.py` 小智协议子集实现（WS `/xiaozhi/v1/`：hello 鉴权（预共享 token，与 record 协议同源）、二进制 Opus 帧、`listen/tts/stt` 状态消息、`tts.stop` 打断、`set_scenario` MCP 调用与结果、`practice` report/tick 下发）；`pipeline.py` 对话管线（能量 VAD 静音判停约 0.8s → Opus 解码 → MiMo ASR → LLM 结构化输出 `{reply, score, feedback}`（system prompt = 角色人设 + 场景说明 + 教练指令）→ TTS 流式 PCM16 → Opus 编码分帧回传）；`engine.py` 模型抽象层（真实 MiMo 实现 + `mock` 实现，env `PRACTICE_MOCK_MODELS=1` 切换，供冒烟） |
| `app/main.py` | 挂路由 | 注册 `/xiaozhi/v1/` WS 路由；沿用现有 `{data, error}` 与日志约定 |
| `requirements.txt` | 增依赖 | `opuslib`（Opus 编解码，需系统 libopus；ASR/TTS 音频为 16kHz/16bit/mono） |
| `scripts/smoke.sh` | 扩冒烟 | 新增 practice 流程：mock 模型下 WS hello → set_scenario（含 `SCENARIO_NOT_FOUND` 分支）→ 模拟音频上行 → 校验 stt/tts 消息序列、逐轮落库、结束 report 下发与 overall_score；沿用独立 `smoke.db` 模式可重复执行 |
| `.env.example` | 补配置 | practice 相关（mock 开关等），MiMo key 沿用现有 |

评分与会话收尾：每轮 user 发言经 LLM 结构化输出得到逐轮 `score`/`feedback` 落 `practice_turn`；会话结束（时长用尽/设备主动结束/断连超 5 分钟）计算 `overall_score`（逐轮均分）写 `practice_session` 并下发 `practice.report`。LLM 超时（首 token >5s）回退固定话术，TTS 失败降级文本上屏（`stt`/文本消息），对齐 MVP 文档 §8。

## 5. 验证步骤

1. **服务端**：`cd peilian/server && bash scripts/smoke.sh` —— 全绿，含新增 practice 流程（mock 模型）；`curl /health` 正常。
2. **固件构建**：`source ~/esp/esp-idf/export.sh && cd peilian/firmware/xiaozhi-esp32 && python3 scripts/build.py --list-boards && python3 scripts/build.py folotoy/ai-passport`（或 `idf.py set-target esp32c3 && idf.py build`），编译通过且 app 分区 < 2.9MB。
3. **固件 host 测试**：`python3 -m unittest discover -s scripts/tests -v` 通过；clang-format 仅格式化触碰文件。
4. **本地端到端（无真机）**：服务端起 mock 模型 + 一个 Python 小脚本模拟设备 WS 客户端（hello→set_scenario→发音频→收 report），验证协议序列；固件侧逻辑以构建 + 代码走查覆盖。
5. **待真机项（如实报告）**：三键交互、屏幕渲染、扬声器/麦克风链路、打断体感、首轮响应 ≤3s，需硬件验证。
